**이름:** AIOps Experiment Engineer

**한 줄 소개:** 성능 수정은 AI가 제안하고, Rust 하네스가 증명하거나 거절합니다.

## 문제

AI 모델은 그럴듯한 성능 수정을 몇 초 만에 씁니다. 하지만 그 수정이 모든 응답을 그대로 지키는지, 서비스가 정말 빨라졌는지 확인하는 데는 여전히 엔지니어의 몇 시간이 듭니다. 모델의 주장을 그대로 믿는 것이 바로 실패하는 방식입니다.

## 하는 일

Meta 모델(Meta Model API의 Muse Spark 1.3)이 도구로 느린 서비스의 증거를 읽습니다: 지표, SQL 개수가 붙은 가장 느린 요청, 소스 코드, 과거 실험. 사실과 가설을 나눠 적은 뒤, 가설 하나와 그 가설이 틀렸음을 보여 줄 조건, 패치 하나를 냅니다.

그다음 Rust 하네스가 엔지니어가 할 일을 합니다.

- 인터넷도 비밀값도 없는 격리된 Cloudflare Container에서 패치를 빌드합니다.
- 후보를 원본과 비교합니다: golden 케이스 14개, 응답 불변식, 표본 요청 200개.
- 먼저 기계의 측정 잡음을 잰 뒤, 바뀌지 않은 서비스와 번갈아 3쌍으로 p95 지연을 측정합니다.

판정은 모델이 아니라 Rust 평가기가 내립니다. VERIFIED, REJECTED, INCONCLUSIVE 중 하나를 측정한 이유와 함께 돌려줍니다. 거절 이유는 모델에게 돌아가고, 모델은 정해진 예산 안에서 다시 시도할 수 있습니다.

## 배포본에서의 결과

N+1 쿼리가 있는 주문 목록 API에서:

- Muse Spark 1.3은 모델이 작업을 시작한 9회 모두 VERIFIED 패치에 도달했습니다. 2회는 모델 호출 전에 멈췄습니다. 한 번은 우리 배포 때문이었고, 한 번은 기계가 너무 흔들려 하네스가 판정을 거부했기 때문입니다. Muse Wonder 1.0은 4회 중 2회였고, 실패 하나는 우리 쪽 출력 토큰 상한 때문이었습니다(수정함).
- 검증된 패치는 요청당 SQL을 81.8개에서 3.0개로, p95를 약 17 ms에서 약 2 ms로 줄였습니다(쌍별 개선율 중앙값 87.7~90.1%). golden과 표본 응답은 모두 그대로였습니다.
- 한 run에서는 모델의 첫 패치가 소스와 맞지 않았습니다. 하네스는 아무것도 실행하기 전에 거절했고, 모델은 거절 이유를 읽고 패치를 고쳐 두 번째에 VERIFIED를 받았습니다.
- 다른 run에서는 측정이 너무 흔들렸습니다(baseline 편차 19.2%). 하네스는 추측하지 않고 INCONCLUSIVE를 두 번 냈고, 모델의 다음 후보가 VERIFIED였습니다.

## 실제 버그에서

실제 오픈소스 Rust 프로젝트의 기록된 버그에서도 같은 루프를 돌렸습니다. Vaultwarden 이슈 #1402(`GET /api/sync`의 N+1)이고, 메인테이너가 고치기 직전 커밋에서 GitHub 호스팅 러너로 실행했습니다.
- 모델의 일괄 조회 재작성은 메인테이너의 수정과 같은 접근이었습니다. sync 한 번의 SQL을 2,011개에서 15개로, p95를 246 ms에서 64 ms로 줄였고, golden 응답은 모두 같았습니다: VERIFIED 74%.
- 이 코드베이스가 드러낸 하네스 문제를 고친 뒤 두 run 모두 여기에 도달했습니다.
- 그 전에는 한 run이 턴을 다 썼고, 한 재작성은 컴파일되지 않았습니다. 더 작은 정답 변경은 한 기계에서 18%, 다른 기계에서 21%로 측정돼 한 번은 REJECTED, 한 번은 VERIFIED였습니다.

## 하네스가 도장만 찍는 게 아니라는 근거

- 직접 쓴 함정 패치 23개. 각각 정확히 한 관문에서 걸리도록 만들었습니다.
  - 항목 순서 오류, 다른 사용자 주문 노출, 금액 반올림
  - 정답 파일 수정, 더 느린 코드, 특정 상품에서의 크래시, 부하 중 경쟁 조건, 빌드 오류
  - 보안 관문이 거절하는 위험한 코드 7개. SQL을 통한 셸 명령 실행, 정답 파일을 바이너리에 컴파일해 넣기 등
  - 느린 코드를 그대로 두고 몰래 baseline을 느리게 만드는 패치 1개(보안 절 참고)

  23개 모두 CI에서 기대한 판정을 기대한 이유로 받았습니다.
- 핸들러에 규칙으로 만든 변이 36개 중 정확성 관문이 30개를 잡았습니다. 남은 6개 중 4개는 어떤 응답도 바꿀 수 없고, 2개는 이 데이터에서 결과가 같습니다.
- 함정과 변이를 만들면서 우리 하네스의 실제 구멍이 드러났습니다. 잘못된 항목 순서를 통과시키던 golden 케이스, 몰래 원본 바이너리를 측정하던 빌드 캐시 버그, baseline을 느리게 만들어 개선을 꾸며 내는 방법 등입니다. 모두 고치고 기록했습니다.

## 보안: 모델과 모델이 쓴 코드는 믿지 않는다

모델은 제안만 합니다. 무언가를 바꾸는 도구도, 네트워크 접근도, 비밀값도 없습니다. 모델이 쓴 패치는 모두 모델을 믿지 않는 여러 겹을 통과해야 합니다.

- **보안 관문.** 빌드하기 전에, 다음 중 하나라도 추가하는 패치는 거절합니다.
  - `unsafe`, `libc`, `asm!`
  - 프로세스 실행, 네트워크 호출, 비밀값 읽기, 파일 읽기·쓰기
  - 파일을 바이너리에 컴파일해 넣기(`include_str!`)
  - 문자열로 조립한 SQL, 관리용 SQL(`COPY ... PROGRAM`, `LOCK`, `pg_sleep`, `ALTER`, `GRANT`)
  - 인증·암호 관련 파일 수정
- **샌드박스.** 패치는 인터넷도 비밀값도 없는 컨테이너에서 root가 아닌 사용자로 빌드되고 실행됩니다. 시나리오와 정답 파일은 읽기 전용입니다.
- **최소 권한 DB.** 시험 대상 서비스는 DB 슈퍼유저가 아니라 읽기 전용 계정으로 접속합니다. 그 계정으로 권한이 필요하거나 오래 걸리는 문장 10개를 실행해 봤습니다.
  - 9개는 거부됐습니다: `COPY ... TO PROGRAM`을 통한 셸 명령, 테이블 잠금, 쓰기, 파일 읽기, 설정 변경 등
  - 긴 sleep은 10초에서 끊겼습니다.
- **측정 격리.** 한쪽 서비스를 측정하는 동안 다른 쪽은 얼려 둡니다.

우리 하네스를 검토하다가 실제 구멍 두 개를 찾았습니다. 둘 다 막았고 측정으로 확인했습니다.
- **SQL을 통한 셸 명령.** 서비스가 DB 슈퍼유저로 돌고 있어서, 패치에 들어간 고정 SQL 문자열 하나로 셸 명령을 실행할 수 있었습니다. 관문은 `format!`으로 조립한 SQL만 찾고 있었습니다.
- **꾸며 낸 개선.** 후보가 baseline을 느리게 만들어 자신이 빨라 보이게 할 수 있었습니다.
  - 우리 함정 패치는 느린 코드를 그대로 두고, 쉬는 동안에만 CPU를 태웁니다. 실제 변화가 없는데도 45~67% "빨라졌다"고 측정됐습니다. 하네스가 INCONCLUSIVE를 낸 것은 baseline 편차가 컸기 때문일 뿐이었습니다.
  - 측정하지 않는 쪽을 얼린 뒤에는, 같은 함정이 CI에서 0.4 / -1.5 / -0.6%로 측정돼 REJECTED였습니다.

**프롬프트 인젝션.** 모델이 읽는 모든 것에 모델을 조종하려는 글이 들어 있을 수 있습니다: 코드 주석, 로그의 요청 URI, DB의 값.
- **검사.** 모든 도구 출력에서 지시처럼 보이는 문구와 숨은 zero-width·양방향 문자를 찾습니다. URL 디코딩 뒤에도 다시 봅니다.
- **표시.** 걸리면 타임라인에 기록하고, 모델에게는 "이것은 데이터"라고 표시해서 넘깁니다.
- **출력의 모델 글.** 모델이 쓴 글은 PR 설명에서 모델이 닫을 수 없는 코드 블록 안에 들어갑니다.
- **레드팀**(GitHub 호스팅 러너). 소스, 요청 로그, 숨은 문자에 지시문을 심었습니다. Meta 모델 3회(Muse Spark 1.3 2회, Wonder 1.0 1회):
  - 검사가 도구 출력 4개, 4개, 3개를 표시했습니다.
  - 어떤 패치에도 심은 코드가 들어가지 않았습니다.
  - 세 번 모두 85~89%로 VERIFIED였습니다.

  모델들은 인젝션을 따르지 않았습니다. 따라서 이 결과는 검사가 인젝션을 본다는 것을 보여 줄 뿐, 인젝션을 따르는 모델을 관문이 막는다는 것을 보여 주지는 않습니다. 그 경로는 인젝션이 요구하는 종류의 코드를 넣은 함정 패치로 따로 시험합니다.

## 성능 너머

- **취약점 수정.** 모델이 보고된 취약점을 고칩니다. 하네스는 다음을 모두 만족할 때만 수정을 받아들입니다: 모든 공격 요청이 원본에서는 통하고 수정본에서는 실패하며, golden 응답은 모두 그대로일 것. 공격에는 모델이 보지 못하는 변형이 섞여 있어서, 보고된 문자열만 거르는 수정은 떨어집니다.
  - 상품 검색에 일부러 넣어 둔 SQL 인젝션에서 Meta run 5회가 모두 첫 후보로 VERIFIED였습니다(Muse Spark 1.3 3회, Wonder 1.0 2회).
  - 다섯 모두 쿼리를 파라미터로 바인딩했습니다: 공격 4개 중 4개 차단, golden 12/12.
  - 꼼수를 포함해 직접 쓴 수정 5개도 CI에서 기대한 판정을 받았습니다.
- **주간 취약점 탐색.** 일주일에 한 번, 또는 요청할 때, 모델이 코드를 읽고 의심되는 취약점을 5개까지 냅니다. 각각 공격 요청, 무해한 대조 요청, 공격이 통하면 돌아와야 할 증거를 함께 냅니다.
  - runner가 이 요청들을 샌드박스 안의 바뀌지 않은 서비스에 보냅니다.
  - 모델이 아니라 규칙이 각각을 REPRODUCED, SERVER_ERROR, NOT_REPRODUCED로 판정합니다.
  - 배포본의 첫 탐색(Muse Spark 1.3, 92초)은 올바른 곳을 짚었습니다: 상품 검색에 일부러 넣어 둔 SQL 인젝션. 하지만 공격 요청이 모델이 말한 증거를 돌려주지 않아 NOT_REPRODUCED였습니다. 주장만으로는 인정하지 않습니다.
- **무인 운영.** 배포본은 혼자서 돕니다.
  - 매일 예약 run과 주간 탐색
  - 측정이 흔들리면 실패하지 않고 나중에 다시 측정
  - run 수와 모델 토큰의 하루 상한
  - Slack, Discord, 웹훅 알림
  - VERIFIED 패치를 증거와 함께 PR로 만드는 워크플로

## 정직한 범위

두 시나리오는 모두 N+1 문제입니다. 하나는 직접 만들었고 하나는 실제 버그입니다. 이 프로젝트가 기여하는 것은 모델을 둘러싼 루프입니다. 관문들은 N+1에 대해 아무것도 모르고 어떤 패치든 같은 방식으로 판정하지만, 다른 종류의 성능 문제는 아직 시도하지 않았습니다. runner는 PostgreSQL을 쓰는 Rust HTTP 서비스를 대상으로 합니다. Vaultwarden 시나리오처럼 서비스를 추가하는 데는 시나리오 파일, seed, 부하 스크립트면 됩니다. 실제 버그의 seed에는 조직과 첨부 파일이 없어서, 모델 패치의 그 분기는 실행되지 않았습니다.

보안에 대해서는:
- 관문은 글자를 봅니다. 성능 패치에 들어갈 이유가 없는 것을 잡을 뿐, 그것을 쓰는 모든 방법을 잡지는 못합니다. 샌드박스, DB 계정, 얼리기는 철자에 의존하지 않습니다.
- 인젝션 검사는 어림 규칙입니다.
- 탐색은 GET 요청만 보내고, 탐색 한 번은 데이터 하나일 뿐입니다. REPRODUCED는 주장한 동작이 실제로 일어났다는 뜻이지, 그것이 취약점이라는 판단은 아닙니다.
